# AI 협업 기록

## 과제와 주제 선택

교육 과정의 팀 프로젝트가 막바지라 과제에 사용할 시간이 넉넉하지 않았다. 그렇다고 기능 하나를 단순 생성하는 데 그치기보다, 요구사항을 정하고 생성 결과를 검토하며 전체 업무 흐름을 완성하는 방식으로 AI를 활용하고 싶었다.

B2B SaaS를 직접 만드는 것이 개발자가 된 계기였고, 채용 설명회에서 회사가 B2B 플랫폼, 하이브리드 실행, 워크플로우 제어, 엔터프라이즈 RAG와 폐쇄형 구축을 중요하게 다룬다는 설명을 들었다. 이 방향을 작게나마 보여 줄 수 있는 업무로 정산 검수를 선택했다. 백엔드 교육에서 배운 Java와 Spring을 중심에 두고, AI는 정책 근거 설명에 제한해 업무 시스템에서의 안전한 사용 방식을 표현하려 했다.

## 처음 AI에 전달한 요구

- Spring Boot로 실행 가능한 정산 검수 백엔드를 구성함
- CSV의 금액 초과, 증빙 누락, 중복 결제를 확인함
- AI API 키가 없어도 프로젝트를 실행할 수 있게 함
- MySQL을 사용하고 샘플 데이터와 실행 문서를 제공함
- 회원가입·로그인, 정책 문서, 검수 이력, React 화면, RAG까지 단계적으로 확장함
- 코드 주석은 `// ...함`, `// ...임`, `// ...만듦`처럼 간결한 명사형으로 작성함

처음부터 “AI는 설명만 해야 한다”는 구조를 정한 것은 아니었다. AI와 구현 범위를 나누는 과정에서 금액·중복·증빙 판정까지 생성형 AI에 맡기면 같은 입력의 결과가 달라지고, API 장애가 핵심 업무를 멈출 수 있다는 문제를 확인했다. 그 결과 규칙은 Java가 확정하고 AI는 정책 검색과 설명만 담당하는 구조로 수정했다.

## AI가 제안한 내용

- 검수 규칙을 공통 인터페이스와 독립 구현체로 분리하는 구조
- AI 연결부를 인터페이스 뒤에 두고 기본 설명 구현을 제공하는 구조
- 구조화된 AI 응답과 timeout·오류 fallback 처리
- JPA 엔티티와 Repository를 이용한 저장 구조
- 초기 단일 정적 화면과 이후 React 분리 선택지
- Python FastAPI와 Chroma를 별도 RAG 서비스로 구성하는 방식
- 배치, 거래, 위반, 설명, 담당자 판단을 구분한 데이터 모델
- 단위 테스트, API 통합 테스트, 프론트 테스트를 나눈 검증 방식

## 그대로 채택하지 않고 결정한 내용

1. AI 판정은 거절함

   금액 초과와 중복 여부는 재현 가능한 Java 규칙으로 확정하고 AI에는 결과 설명만 맡김.

2. AI 장애의 전체 `500` 처리는 수정함

   RAG 호출이 실패해도 규칙 결과와 배치 저장이 남도록 `RULE_FALLBACK` 설명을 생성함.

3. JPA 제안은 JDBC로 단순화함

   현재 저장 흐름은 명시적인 insert와 소유권 조건 조회가 중심이라 객체 변경 감지보다 실행 SQL과 트랜잭션을 직접 확인하기 쉬운 `JdbcTemplate`이 적합하다고 판단함. 데이터 관계와 동적 조회가 크게 늘면 JPA 전환을 검토함.

4. 정적 화면 결정은 요구 확대 후 변경함

   최초 MVP에는 별도 React가 과하다고 보았지만 회원가입, 정책 등록, 배치 상세, 담당자 판단이 추가되면서 화면 상태와 API 테스트의 필요성이 커짐. 이 시점에는 React 분리가 오히려 구조를 명확히 한다고 판단해 결정을 바꿈.

5. 거래 원문 전체 저장은 제외함

   업로드 파일 자체는 개인정보와 보존 정책이 정해지지 않은 MVP에서 보관하지 않음. 대신 과거 검수 재현에 필요한 정규화 필드, 위반, 설명과 판단만 저장함.

6. API 키의 소스 삽입은 거절함

   Python 파일이나 Java 설정에 실제 키를 쓰지 않고 `.env`와 환경변수로 전달함. 저장소에는 키 이름과 예시만 둠.

## 반복 과정에서 발견하고 수정한 문제

- macOS에서 Windows 줄바꿈으로 `gradlew` 실행이 실패해 LF와 실행 권한을 수정함
- 이미 실행 중인 서버의 8080 포트 점유를 코드 빌드 실패와 분리해 확인함
- `.env`가 Spring Boot에서 자동 로드되지 않아 설정 import 경로를 보완함
- MySQL 전환 뒤 H2 테스트를 MySQL 호환 모드로 맞추고 테스트별 DB 데이터를 초기화함
- H2와 MySQL의 생성 키 반환 차이로 배치 저장 테스트가 실패해 JDBC 키 조회 방식을 호환되게 수정함
- Vite 프록시 주소가 실제 Spring 서버와 맞지 않아 로그인 요청이 실패한 문제를 수정함
- CSV 업로드 뒤 폼 초기화 시 선택 파일까지 먼저 사라지는 문제를 처리 순서 수정으로 해결함
- RAG 호출 예외가 배치 전체 롤백으로 이어질 수 있어 규칙 기반 fallback 경계를 서비스에 추가함
- 다른 사용자의 배치 상세 접근을 막기 위해 배치 소유자와 관리자 조건을 API 테스트로 확인함

## 결과가 발전한 순서

1. Java 규칙과 CSV 검증으로 재현 가능한 검수 핵심을 만듦
2. AI 연결 인터페이스와 키 없는 기본 설명으로 실행 가능성을 확보함
3. MySQL, 회원가입·로그인과 권한을 추가해 사용자 경계를 만듦
4. 정책 문서 등록과 Python·Chroma RAG로 근거 검색을 연결함
5. 배치·거래·위반·설명을 영구 저장해 과거 결과 조회 기반을 만듦
6. React 화면에서 로그인부터 업로드와 상세 확인까지 연결함
7. RAG 장애 fallback과 담당자 판단 이력을 추가해 업무 흐름을 마무리함

## 최종 코드를 이해하고 검증한 근거

- 금액 초과, 증빙 누락, 중복 결제 규칙의 입력과 기대 결과를 단위 테스트로 확인함
- MockMvc로 회원 권한, CSV 업로드, 배치 저장, 상세 조회, 다른 사용자 접근 차단과 fallback을 확인함
- React 테스트로 로그인, 업로드 오류, 검수 결과와 위반 코드 표시를 확인함
- Gradle 전체 테스트, Vitest, Vite 프로덕션 빌드와 Python 단위 테스트를 각각 실행함
- 실제 브라우저에서 회원 로그인, 샘플 CSV 업로드, 배치 상세, AI 설명과 담당자 판단 흐름을 확인하고 화면을 저장함
- MySQL의 테이블과 저장 결과를 확인하고 제출용 테스트 기록을 정리함

AI는 초안과 선택지를 빠르게 만드는 도구로 사용했다. 최종 구조는 제안의 장단점을 비교해 범위를 바꾸고, 실패 결과와 테스트를 근거로 직접 수정하면서 확정했다.
